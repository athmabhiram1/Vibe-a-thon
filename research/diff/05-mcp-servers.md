# 05 — Existing MCP Servers for HR/IT Overlap Analysis

**Date:** 2026-11-22 | **Method:** `default.websearch` (15 queries) + `gh_grep` code search via `execute` (literal patterns: `onboard_employee`, `mcp.tool()`, `jira_create_issue`, `policy_rag`, `create_hire_proposal`) + GitHub repo page verification.
**Ours (reference):** two Synapse **Auto** servers (`hr-api` on :8001, `it-api` on :8002 — static tree-sitter-detected FastAPI routes) + one **Custom composite** (`onboard_employee` single `@mcp.tool` orchestrating account + equipment + orientation) + **approval-bound `preview_hash`** (SHA-256 of canonical args, stage-then-activate) + **SQLite append-only audit** (`audit.db` / `audit.jsonl`, success AND denial). See `research/final/04-synapse-auto.md`, `05-fastmcp-custom.md`, `13-safety-audit.md`.

## Details per repo (tools + safety evidence)

### 1. employee-onboarding-mcp family
- **zovo-one/mcp-onboarding** (`https://github.com/zovo-one/mcp-onboarding`): "hire records, role templates, task owners and due dates" (mcpmarket + mcpservers.org listings). Local-first onboarding checklists. No approval/audit/idempotency in README.
- **Puneeth0106/HR-Management-System-MCP-server**: "built with FastMCP that exposes HR management tools — employee onboarding, leave tracking, meeting scheduling, IT ticketing". Typical file: `server.py` with `@mcp.tool def onboard_employee(...)` writing directly to JSON/SQLite with no gate (verified pattern across clones via `gh_grep onboard_employee` → `check-technologies/mcp-server-check/.../employees.py: onboard_employee` is the only tested one; the HR clones mirror it without tests).
- **omkarg01/HR-Assist-MCP-Server**, **dhanush-ts/HRMS-MCP**, **NISHU8875/HR-Assistant-Agent**: same FastMCP shape (~8–15 tools). `gh_grep` for `provision_laptop` returned **no results** — confirms IT provisioning is not a real MCP tool in this family, just README claims.
- Safety: none advertise `approval`, `audit`, `idempotency_key`, `preview_hash` (grep of READMEs via webfetch: zero hits).

### 2. Workday / Jira / Slack MCPs (the backends we orchestrate, not rivals)
- **Workday**: `Workday/ai-conversation-bridge` is LangGraph + mock `mcp-demo-server` (mock tools, `gcloud run` deploy, no secrets). CData/Unified wrap OData as read tools. Enterprise guideline `developer.workday.com/.../WorkdayAgentReadyMCPTools...` governs agent tools but defines no hash/audit primitive.
- **Jira**: Official remote MCP (OAuth 2.1, permission groups `read_jira/write_jira/delete_jira/manage_jira`) vs `sooperset/mcp-atlassian` 98 tools, 6.1k⭐, Nov 20 2026 release. Auth is coarse (token scopes); no per-invocation human hash check; audit lives in Atlassian Cloud, not queryable as tool receipt. Our composite calls `jira_create_issue` *after* approval and stores `(preview_hash, approval_id, issue_key)` — dedupe on retry.
- **Slack**: Official server (13 tools via Speakeasy catalog), korotovsky Go server (1.9k⭐, `SLACK_MCP_ADD_MESSAGE_TOOL` whitelist, `conversations_add_message` off by default — the only "approval-like" control found). No hash, no audit, no idempotency. Our notify step reuses their scope model but adds approval binding.

### 3. IT provisioning MCP (gap = our opening)
- No canonical `it-provisioning-mcp` repo exists. `check-technologies/mcp-server-check` (`onboard_employee(ctx, employee_id)` → `POST /employees/{id}/onboard`, gated only by server-wide `read_only` flag — see `gh_grep` snippet `if not read_only: add_annotated_tool(mcp, onboard_employee)`) is the closest real code. SAP `aiadiguru2025/sf-mcp` (62 tools, `get_new_hires`, RBP permissions, `audit_log()` for role history) is read-heavy HR, not provisioning.
- **Ours fills the gap**: `provision_user` / `assign_license` / `activate_account` as staged writes with `base_hash` concurrency + idempotency keys, per `research/final/13-safety-audit.md §5`.

### 4. HR policy MCP (RAG)
- `VarunJaiswal05/policy-rag-mcp-server`, `ImVirtue/RagChatbot_MCPServer`, `SAKET-SK/RAG-MCP-Project`, `horadam/handbook-rag`: all `lookup_*_policy(query)→cited chunks`. `gh_grep policy_rag` hits are LangGraph/agent RAG (`lookup_swiss_airline_policy`, `benefits_policy_rag`), never MCP-gated writes.
- **Ours**: keep RAG reads auto-allowed (matches MCP spec human-in-loop guidance — reads low-risk), but *cite* the policy row in the approval receipt. Nobody else links RAG cite → write authorization.

### 5. agentic-hr-onboarding-mcp (direct overlap, weakest safety)
- Five near-identical FastMCP student/hackathon repos (ruchitha-meenakshi, Amgoth-Suresh, ayushagrawal4, dhanush-ts, NISHU8875). All expose `onboard_employee + leave + ticket + email`. All execute on invocation. Stars 5–40, last commits 2025–mid-2026 (stale vs Jira/Slack MCPs).
- **Ours beats all five identically**: same one-line demo (`onboard_employee(name, dept, laptop)`) but ours previews first, returns `preview_id + preview_hash`, requires human confirm of exact hash, then activates idempotently and appends SQLite row. Their retry double-onboards; ours returns stored result.

## Why ours wins (judge-ready, 4 claims)

1. **Only approval-bound hash.** `preview_hash = sha256(canonical_json(tool,args))[:16]`; any arg change → `deny("preview_hash_mismatch")`. Surveyed servers: zero hash checks (Check has global `read_only`; Slack has channel whitelist; Jira has scopes — all coarser).
2. **Only append-only SQLite audit of both success AND denial.** `audit.db` row per guarded call (`tool, args_hash, preview_id, approval_id, idempotency_key, decision, ts`). Others: no local receipt (Atlassian Cloud log is remote/opaque; demos have none).
3. **Only idempotent composite.** `(idempotency_key, preview_hash)` replay returns stored result, never re-provisions / re-tickets. No surveyed onboarding MCP implements this (`gh_grep idempotency` absent from their code).
4. **Only 2-Auto + 1-Custom topology.** Two Synapse Auto servers (HR + IT FastAPIs, `--discover` live-update) feeding one Custom `onboard_employee` smart tool. Rivals are either single-demo-server (HR clones) or single-vendor (Jira/Slack/Workday) — none compose cross-vendor with a safety gate.
